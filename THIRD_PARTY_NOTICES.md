## RFC 8032 test keys

Tests, fuzz targets, and the grant test vectors sign with the published Ed25519 test keys of
[RFC 8032](https://www.rfc-editor.org/rfc/rfc8032) (Josefsson, Liusvaara, "Edwards-Curve Digital
Signature Algorithm (EdDSA)", January 2017), section 7.1 (TEST 1, TEST 2, TEST 3, TEST 1024,
TEST SHA(abc)) and section 7.2 (the Ed25519ctx key, used as a plain Ed25519 key). The key values are
copied unmodified. They appear in, for example, `tests/vectors/grant-v1/manifest.json`,
`tests/vectors/grant-v1/gen/src/generate.rs`, `broker/tests/common/mod.rs`, and
`crates/nodkey-grant/tests/common/mod.rs`. Their secrets are public: **they are test-only keys**.

The signatures and grants in `tests/vectors/` were generated by this project's own generator with
those keys; they are not copied from the RFC.

- RFC 8032 carries the notice "Copyright (c) 2017 IETF Trust and the persons identified as the
  document authors. All rights reserved." and is subject to BCP 78 and the
  [IETF Trust Legal Provisions](https://trustee.ietf.org/license-info) (TLP).
- RFC 8032 is a document of the IRTF stream, not the IETF stream. Section 8.g of the TLP (version 5.0)
  states that section 4 of the TLP, which licenses "Code Components" under the Revised BSD licence,
  does not apply to IRTF-stream documents. The Revised BSD Code Components licence is therefore **not**
  the basis for this use.
- TLP section 3.c.iii permits copying unmodified portions of IETF documents when each portion is
  attributed to the IETF and identifies the document it is taken from. This section provides that
  attribution: the test keys are taken from IETF RFC 8032, sections 7.1 and 7.2.

## Rust crates (not vendored)

The Rust components depend on third-party crates from crates.io. They are **not** included in this
repository; Cargo downloads them at build time, at the versions pinned in each `Cargo.lock`. Their
self-declared licences are inventoried in
[docs/supply-chain.md, "License inventory"](docs/supply-chain.md#license-inventory). That inventory
records that some of those licences (for example MIT, BSD-3-Clause, ISC, Zlib, BSL-1.0) require their
copyright and licence notices to be kept when binaries are redistributed; a complete notices file for
any binary release is still to be generated.

## Container base images (not redistributed)

The demo stacks, the build images, and some test scripts use the following images, each pinned by
digest in the Dockerfiles, compose files, and scripts that use them. They are pulled from their
registries at build or run time; this repository does not contain or redistribute them. Each image and

| Image (tag as pinned) | Used for |
|---|---|
| `rust:1.99-slim-trixie` | Building the Rust components; the fuzzing container (`tools/fuzz.sh`) |
| `debian:trixie-slim` | Runtime base of the Rust components and simulators |
| `php:8.4-fpm-alpine` | The intentionally vulnerable demo apps |
| `postgres:17-alpine` | The demo databases and the PostgreSQL integration tests |

the README recording. It is referenced by tag, not by digest, in `assets/readme/demo.tape` and

## Open questions for counsel

These are questions, not conclusions:

1. Is copying the RFC 8032 test-key values into source code and test data covered by TLP section 3.c,
   or does it need a licence at all, given that they are short numeric values?
2. Is the attribution in this file sufficient for that use, or must it also appear in each file that
   contains the keys?
3. For a future binary or container image release: which notices from the crates and base images must
   be shipped with it, and in what form?
4. Do the rendered images and outlined paths made from OFL-1.1 fonts need any notice beyond this file?
