# Demo P integration findings

Defects and deviations found while assembling `examples/confirmed-refund/`. Component defects are
recorded here, not patched in the demo.

| ID | Severity | Where | Finding | Disposition |
|---|---|---|---|---|
| DEMOP-F01 | Medium (design gap) | `crates/nodkey-gateway` (spec gap GW-6) | A multi-user app that names the approver has no Nodkey-provided way to learn the signed-in subject, so the demo shop uses an untrusted customer hint when proposing. The broker and authority still bind approval to the intended approver and check ownership, so a wrong hint can only produce a proposal nobody can approve. | Open: specify an identity hint the gateway supplies to the app (non-authoritative), or document the hint as untrusted UX only. |
| DEMOP-F02 | Low (environment) | Colima virtiofs bind mounts | Bind-mounted files do not keep their host ownership inside the VM. The adapter correctly refused to start (`config.json owned by the adapter or broker uid`). | Fixed in the demo: adapter inputs are copied into named volumes by a one-shot `adapter-init` service with the required owners and modes. |
| DEMOP-D01 | Info (deviation) | `tests/demop/run.sh` test PKI | simpay certificates are valid 2025–2035 rather than 7 days, and carry no IP SAN. | Test-only PKI; the CA private key is deleted after issuance. Shorten validity when the harness gains a certificate-expiry test. |
| DEMOP-F03 | Low (spec inconsistency) | `docs/specs/payments-adapter-v1.md` PT-32 vs §3.1 / §10 | PT-32 expects a start-up refusal when `retention_s` is configured above simpay's retention, but §3.1 makes `retention_s` the operator's statement of the provider's retention and §10 says the adapter cannot check it. Observed: adapter with `retention_s: 400` (simpay `idempotency_retention_s: 300`) starts. Repro: `tests/demop/run.sh` → PT-32c. | **Resolved (spec, Draft 3.3):** `docs/specs/payments-adapter-v1.md` §3.1 and §10 state `retention_s` as an unverifiable operator statement; PT-32 now tests the start-up rule against the configured value (`tests/demop/harness.py` PT-32c: `retention_s` 240 → refused). No code change. |
| DEMOP-F04 | Low (spec / implementation mismatch) | `broker` strict framing vs PT-10 | A propose line with a duplicate `amount_minor` key is rejected (no record), but with `malformed_request`, not `invalid_argument` as the PT-10 row states (effect-protocol-v2 §1.2 framing rejects duplicates without naming the code). Repro: PT-10b. | **Resolved (spec, Draft 3.3):** PT-10 row amended: duplicate key → `malformed_request` (effect-protocol-v2 §1.2 framing); `tests/demop/harness.py` PT-10b updated. No code change. |
| DEMOP-F05 | Low (spec inconsistency) | `payments-adapter-v1` PT-18 vs §6.2 | `hostile_error_text` (400 with an unknown error code) is classified `refused/other_4xx`, which §6.2 specifies (`other_4xx` is a `RefusalCode`); the PT-18 row expects `ambiguous`. Safety outcome holds: row UNKNOWN + alarm, reconciled to SUCCEEDED, ledger 1, no provider text anywhere (PT-18z). Repro: PT-18h. | **Resolved (spec, Draft 3.3):** PT-18 row amended to §6.2: `hostile_error_text` → `refused/other_4xx`, row `UNKNOWN` + alarm, resolved by lookup; `tests/demop/harness.py` PT-18h expects `refused/other_4xx` and checks the charge counters. No code change. |
| DEMOP-F06 | Medium (design gap: spec + broker) | `broker/src/v2/payments.rs` settlement polling; spec §7.3 vs PT-23 | Settlement is polled only for rows with `settlement = 'pending'`. simpay creates refunds `succeeded`, and `late_refund_failed` moves them to `failed` afterwards; the broker never looks again, so the row keeps `settlement = succeeded` and no `refund_settlement_failed` alarm is raised. The amount stays encumbered (as PT-23 wants). Repro: PT-23 (simpay ledger shows the refund `failed`; `payment_effect.settlement = 'succeeded'`; no new broker alarm). | **Resolved (broker + spec, Draft 3.3 §7.3 post-success watch):** `broker/src/v2/payments.rs` (`poll_settlement`, `watch_next`, scan of `settlement IN ('pending','succeeded')`), `broker/src/v2/config.rs` (`payments.settlement_watch_s`, default 30 days, 1 h ..= 90 days), DB guard in `examples/php-ledger/docker/postgres/initdb/03-payments.sh` (allows `succeeded → failed` only). A reversal → `settlement = failed`, `anomaly = settlement_reversed`, alarm `refund_settlement_failed`, amount encumbered; lookup only, never re-dispatched. Tests: `broker/tests/pg_payments.rs` `f06_reversal_after_success_is_recorded_without_resend`, `f06_watch_is_bounded`; PT-23 (`after_s: 20`). PT-43's "nothing sent" check is now limited to the probe's own requests (by correlation id), because the watch legitimately sends `refund.get` for other rows. Residual for reversals after the window (§10). |
| DEMOP-F07 | Low (spec claim vs PostgreSQL behaviour) | DB roles, PT-31 / PA-17 | `ALTER ROLE nodkey_broker SET search_path = 'public'` **succeeds** when run as `nodkey_broker` (PostgreSQL 17 lets an ordinary role set its own session defaults). The harness ran it in a rolled-back transaction; `rolconfig` stays `search_path=""`. Impact appears limited because the role has no `CREATE` on any schema and no `TEMPORARY`, so nothing can shadow `nodkey.*`, but PT-31 states ALTER ROLE is refused. Repro: PT-31 (`alter_role` not refused). | **Resolved (spec + DB, Draft 3.3 §2 PA-17):** the spec no longer claims `ALTER ROLE` is refused; the stated control is schema-qualified SQL, pinned function `search_path`, and no `CREATE`/`TEMPORARY` for any Nodkey role on any schema or database. `03-payments.sh` now also revokes PUBLIC `CREATE, TEMPORARY` on databases `postgres` and `template1` (the new test found PUBLIC `TEMPORARY` on `postgres`). Tests: `broker/tests/pg_payments.rs` `f07_no_create_or_temp_anywhere`; PT-31 catalog checks in `tests/demop/harness.py`. |
| DEMOP-F08 | Low (classification) | `crates/nodkey-payments-adapter` HTTP classification vs PT-18 | `header_injection/te_and_cl` is classified `ambiguous/reset_after_send`, the PT-18 row requires `ambiguous/bad_headers` for every non-CRLF variant (`bare_cr` is `bad_headers` as specified). Outcome is still ambiguous, one refund. Repro: PT-18g. | **Resolved (spec, Draft 3.3):** PT-18 row amended: non-CRLF `header_injection` variants → `ambiguous` with any cause (`bare_cr` still `bad_headers`), one refund, no corrupted state; `tests/demop/harness.py` PT-18g checks the charge counters. No code change. |

## Status of the suite

`tests/demop/run.sh` runs the setup row, the legit flow (L-01..L-06), the shop containment probes
(C-*), and the PT-01..PT-44 groups. Each PT row maps to its PT id and SI in the results table.
Rows the stack cannot exercise are NOT TESTED with the reason (crafted signed grants, clock control,
restore drill, HTTP edge cases simpay cannot emit, K_idem rotation drill, exact crash points between
T1 and T2). DEMOP-F03..F08 are resolved (Draft 3.3 of `docs/specs/payments-adapter-v1.md`, §15). Re-run a single group against a running stack
(`run.sh --keep`) with `python3 -I tests/demop/harness.py --root . --out var/demop --no-seed --only <group>`.
Budgets are per customer per UTC day, so a group re-run on the same stack can be denied by its own
earlier refunds.
