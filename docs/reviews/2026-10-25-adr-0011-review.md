# Review: ADR-0011 (propose → confirm → execute)

- **Date:** 2026-10-25
- **Reviewer role:** adversarial reviewer (fresh context; not the author)
- **Scope:** `docs/decisions/0011-propose-confirm-execute.md` (Proposed). Context: ADR-0010, ADR-0003
  "Phase 3 implementation profile", research 07 §3.1–3.3, SECURITY_INVARIANTS SI-05/06/09/10/18/20/21,
  THREAT_MODEL R-18, OPEN_QUESTIONS OQ-11/OQ-12.
- **Method:** time-boxed design review. The attacker is actor C: arbitrary code in the workload (app or
  agent), full control of the app origin, unlimited `effect.propose` calls. In some scenarios C works
  with actor B (an authenticated malicious user). Nothing was executed and no test results are claimed.
  Every finding is a design or specification gap; none is a demonstrated exploit.

## Verdict

**Accept with changes.** Moving write-grant delivery out of the workload is a real reduction in
authority. It removes R3B-04, the HTTP-body binding surface, and the workload's control over *when*
an approved grant is used. I support the direction.

The ADR as written has **two Critical/High gaps that would let an effect execute without the
intended user's approval**:

- **PC-01:** the approver is not bound to a subject.
- **PC-02:** the provenance rule it cites for the approval endpoint, read literally, admits the app
  origin.

It also has one cross-user information leak (PC-03), and it drops hardening by superseding all of
ADR-0003 item 4 (PC-05). These must be fixed in the ADR text, and in SI-20/SI-21, before acceptance.

## Findings

Severity: Critical / High / Medium / Low. "Blocks" means it must be fixed before the ADR is accepted.

### PC-01 — The approver is any authenticated user; the pending effect has no intended subject (High, blocks: yes)

**Scenario.** Step 1 binds a pending effect only to the workload. Step 2 says any subject named by the
workload is ignored and the approving session's subject is used. Possible attacks:

- **(a) Agent workload.** Research 07 §3.1 enrols each agent `wid` to exactly one `(ten, sub)` and
  stores P with `ten`/`sub` from that enrolment (§3.2 step 4). ADR-0011 drops this. A prompt-injected
  agent enrolled for Alice proposes `email.send` or a payment and sends the confirmation URL to Bob,
  for example through an outbound message it is allowed to send. If Bob approves, the effect executes
  under Bob's subject and authority. This is a confused deputy: the agent obtains authority from a
  principal it does not act for.
- **(b) Multi-user web app.** C proposes "refund order 123 to destination D" and sends the link to the
  order's owner, styled as a "confirm your refund" email. The broker's ownership re-check passes,
  because the approver owns the order. Bob sees honest values and approves an effect that he did not
  initiate and that C chose. For operations with no ownership fact, such as outbound messages, the
  approver's identity is simply lent to C.
- **(c) Leaked URLs.** Confirmation URLs can leak through Referer, logs, or chat history. Anyone holding
  one can view and approve the effect under their own subject. The ADR does not require pending ids to
  be unguessable.

**Is this acceptable?** A "payment request link" approved by its recipient is a legitimate product
pattern. It must be **declared per operation**, though, not be the default. Without declaration it
contradicts research 07's agent↔principal binding.

**Fix.**

- When the workload has a trusted principal (an agent enrolment, or a configuration-fixed tenant and
  subject), store `ten`/`sub` on P from that source. Deny approval by any other subject with a uniform
  error.
- For multi-user web workloads, take the intended subject from a gateway-attested request context
  (the session the gateway forwarded when the proposal was made) and never from proposal fields. Allow
  "any subject may approve" only for operations explicitly declared `approver: any`, and say so on the
  page ("This request was created by <app>; it was not necessarily started by you").
- Pending ids must have at least 128 bits of entropy and be single-tenant.
- Rate limits per `(wid, sub)` (research 07 §3.2) need this binding to exist.

### PC-02 — Approval CSRF from the app origin; the cited SI-21 check admits the attacker (Critical, blocks: yes)

**Scenario.** The deployment shape in research 07 is `auth.<domain>` beside the app on the same
registrable domain, so the two are same-site (R-18 by construction). The session cookie is
`SameSite=Lax`. Lax is a cross-*site* control, so it does not stop a credentialed same-site POST.

App-origin script can run `fetch("https://auth.<domain>/confirm/<pid>/approve",
{method:"POST", credentials:"include", mode:"no-cors"})` while the user is logged in. The ADR says only
that "SI-21 provenance checks remain … for the confirmation endpoints themselves". SI-21 as written
accepts a write when `Sec-Fetch-Site: same-origin` or, if that is absent, when `Origin` equals **the
app origin**. Applied literally to the approval endpoint, that is exactly the attacker's origin. Even a
correct reading of "same-origin" is not enough without a token, because some clients omit Fetch
Metadata.

Result: an effect the user never saw executes.

ADR-0003 SI-20 would stop this with a user-verifying WebAuthn assertion. Phase 3 uses test login, so
SI-20's passkey clause is NOT TESTED (profile item 3; research 07 §3.2 step 7). In Phase 3, nothing
named in the ADR prevents it.

**Fix.** The ADR must specify the approval endpoint's own rules:

- **Fetch metadata:** POST only, with `Sec-Fetch-Site: same-origin` relative to the **auth origin** and
  `Sec-Fetch-Mode: navigate` or `cors`. If the header is absent, require `Origin` equal to the auth
  origin. Deny everything else, including `same-site`.
- **CSRF token:** a per-render token bound to `(session, pid, digest)` (see PC-04).
- **Passkeys:** when passkeys land, a WebAuthn UV assertion whose challenge commits to
  `pid ‖ canonical(op, params)`.
- **Tests:** negative tests for a `fetch` from the app origin, a form POST from the app origin, and a
  request with no metadata.

### PC-03 — Confirmation page discloses other users' trusted facts (High, blocks: yes)

**Scenario.** The page shows "broker-resolved trusted facts (for example the order's owner and
remaining refundable amount)". C, or even an uncompromised app that forwards a user-typed order id,
proposes `refund order 777`. Mallory, an authenticated user, opens the link and learns order 777's
owner, its captured and refunded amounts, and whether it exists. Repeating this across ids enumerates
other users' or tenants' orders. This is an IDOR through the confirmation page. Research 07's own
example row 3 displays "customer C-9" for an order the agent's principal does not own.

**Fix.** Resolve and render facts only after checking that the approving subject (and PC-01's intended
subject) is authorized for each referenced resource: owner, or an operator role declared for the
tenant. Otherwise render a uniform "This request cannot be approved by you" page with no facts and the
same response for nonexistent ids. Add a negative test.

### PC-04 — Swap between display and approval: immutability and display binding are not stated (High, blocks: yes)

**Scenario.** The ADR does not say that a pending effect is immutable, or that the approval binds to the
values that were rendered.

- **(a) Mutation.** If `effect.propose` with a reused client idempotency key or the same pid updates
  `params`, C changes the amount or destination after the page renders and before the POST.
- **(b) Race.** C creates P1 (benign) and P2 (malicious) with near-identical rendering and swaps which
  pid the in-page "Approve" refers to (for example by navigating the user between them).

**Fix.**

- P is write-once; any re-proposal creates a new pid.
- The page embeds `digest = H(pid ‖ canonical(op, params) ‖ facts-version)`. The approve POST carries
  it, and the gateway compares it in the same compare-and-set that moves `PENDING → APPROVED`.
- The authority signs from the stored record, never from the POST body.
- The pid is shown visibly on the page.

### PC-05 — Superseding all of ADR-0003 item 4 drops required hardening; SI-20/SI-21/SI-06 contradict the new flow (High, blocks: yes)

**Scenario.** The ADR's status says it supersedes profile items 4 and 7 wholesale. Item 4 also carries:

- `frame-ancestors 'none'`, COOP `same-origin`, and a restrictive CSP on the confirmation page (against
  clickjacking and popup scripting by the app origin);
- "every `ledger.transfer` requires confirmation — no threshold";
- the compare-and-set state machine;
- approval bound to session subject and pid.

Also:

- **SI-20** is still keyed on "an operation the route map marks `confirm`", and the route map no longer
  governs writes.
- **SI-21** defines write-grant issuance by the provenance of the app's HTTP request. Under ADR-0011,
  every write grant is issued on an auth-origin approval, so SI-21 as written is unsatisfiable, or
  falsified.
- **SI-06** lists HTTP path/query/body as binding sources. The new source is "broker-stored proposal".

Invariants outrank ADRs, so the ADR cannot be accepted while it contradicts them.

**Fix.**

- Supersede only the delivery sentence of item 4 (R3B-04 and the `ISSUED` state) and the
  HTTP-binding part of item 7.
- Restate the confirmation-page hardening explicitly.
- Ship the SI-06/SI-20/SI-21 amendments with the ADR: confirmation declared per operation;
  approval-endpoint provenance as in PC-02; binding source = stored proposal.

### PC-06 — Mandate path lets the workload choose whose mandate to spend (High, blocks: yes — one sentence)

**Scenario.** "A proposal that falls entirely within an active … mandate previously approved by the
user skips per-effect confirmation." Proposals carry no trusted subject (PC-01), so the broker cannot
know *which user's* mandate applies unless the workload says so. A compromised multi-user app then
names Alice's mandate to fund an effect requested in Bob's context.

**Fix.** State in the ADR that the mandate lookup key is `(wid, trusted ten/sub)` from enrolment or an
attested context, never a proposal field. For multi-user workloads without attested context, state
that a mandate is standing authority delegated to the workload as a whole (research 07 §3.3 already
assumes one agent ↔ one subject).

### PC-07 — Attacker-controlled free text and look-alike identifiers on the confirmation page (Medium, blocks: no)

**Scenario.** "Broker-stored values" are workload-supplied values, stored verbatim. C can supply:

- a memo or e-mail body reading "SECURITY CHECK — press Approve to cancel the fraudulent transfer";
- bidirectional-override or zero-width characters and newlines that imitate other fields;
- a destination `ACC-1O0042` next to the user's `ACC-100042`;
- an e-mail recipient `support@examp1e.com`.

**Fix.**

- At propose time, reject control, bidi, and zero-width characters in typed fields, and cap lengths.
- Render free text escaped, monospace, and in a box labelled "supplied by <app>, unverified", or omit it
  (research 07 §3.2 step 6).
- Show destination facts the broker resolves: "your account", "not yours", "never used before by you",
  "owned by tenant X" (subject to PC-03).
- Show identifiers in full with no truncation; the R3B-08 display-name residual stays published.

### PC-08 — Approval fatigue and duplicate approvals (Medium, blocks: no)

**Scenario.**

- **(a) Fatigue.** C issues many benign proposals so that the user learns to click Approve, then slips
  in a malicious one.
- **(b) Duplicates.** C says "the first refund failed, please confirm again" and the user approves an
  identical P2. Refunds are bounded by the remaining-refundable re-check, but transfers, payments and
  messages are not, so the effect happens twice.

**Fix.**

- Show on the page how many proposals from this workload are pending for this subject.
- Show any identical effect that executed or is pending in the last N minutes (from broker records).
- Offer a "deny all pending from this app" control.
- Use a short pending TTL.
- Rate-limit per `(wid, sub)` (needs PC-01).
- Publish fatigue as a residual (research 07 already lists R-4).

### PC-09 — Proposal spam exhausts shared broker state (Medium, blocks: no)

**Scenario.** C denying service to *its own* users is out of scope, because it can already refuse to
serve them. But the pending store and the confirmation renderer are shared across workloads, so
unbounded proposals from one `wid` can starve the others. Broker fairness is already NOT TESTED
(D1-07). The ADR names only a per-workload rate limit.

**Fix.** Add a hard cap on concurrent `PENDING` rows per `wid` (and per `(wid, sub)`), proposals
rejected at the cap with a uniform error, expiry sweeping, and a negative test.

### PC-10 — `effect.status` and proposal errors as oracles (Medium, blocks: no)

**Scenario.**

- The ADR does not require `effect.status` to check the caller's `wid` (research 07 §3.2 does). It also
  does not limit what status returns. A sibling workload could poll another workload's pid.
- Status could echo the approving subject, the resolved facts, or upstream error text.
- If `effect.propose` consults trusted state (for example "order not found" vs "not refundable"), it
  becomes an existence oracle with no subject at all.

**Fix.**

- `effect.status` answers only when `P.wid` equals the caller's `wid`, and gives a uniform "unknown" for
  every other pid. It returns only `{state, outcome class, receipt id}`.
- `effect.propose` validates syntax and types only, never facts, and returns uniform errors.
- Fact resolution happens only on the authenticated auth-origin page (PC-03).

### PC-11 — Confirmation-URL phishing and open redirect (Low, blocks: no)

**Scenario.**

- If the page has a "return to app" parameter, C sets it to an attacker site (open redirect on the
  trusted origin).
- C can send users to a look-alike `auth.<domain>` that harvests test-login credentials.

**Fix.**

- No workload-controlled URL parameter on the confirmation page. "Return" goes to a per-`wid`
  registered origin.
- Look-alike phishing is fully addressed only by passkeys (origin-bound WebAuthn). Until then, publish
  it as a residual.

### PC-12 — Overclaims (Medium, blocks: yes — text only)

1. *"The confirmation page shows broker-stored values, not workload-supplied descriptions."* The stored
   values **are** workload-supplied. Only their *binding* is guaranteed, not their meaning (PC-07).
2. *"Compromise of the gateway's HTTP handling or of the broker's request parsing does not let either
   mint authority."*
   - The gateway decides approvals, so a compromised gateway approves anything and the authority signs
     it. This holds only if the authority itself verifies a WebAuthn assertion, which Phase 3 does not
     have.
   - The broker holds the upstream credentials, so a compromised broker needs no grant.

   Restate the claim as: "a compromised *workload* cannot mint authority". Separately, list
   gateway/authority compromise (actor J) as out of scope or as a residual.
3. *"Cannot … delay"*: true only after approval. C chooses when to propose and when to send the user
   the link.
4. *"Smaller workload authority"* is correct only once PC-01 and PC-06 are fixed. Otherwise C gains a
   new ability: borrowing the authority of any user who clicks.

### PC-13 — Grant delivery channel not specified (Low, blocks: no)

**Scenario.** The ADR says the grant reaches the broker "over a channel the workload cannot reach". It
does not say that the broker refuses `cfm`/pid-bound write grants arriving on the workload socket. That
matters if the Reversal path re-enables workload presentation for some operations.

**Fix.** The broker accepts pid-bound grants only on the authority socket (`SO_PEERCRED`-checked).
Workload-presentable grants are a distinct kind.

## ADR-0003 Phase 3 profile items made redundant by ADR-0011

| Item | Status under ADR-0011 |
|---|---|
| 1 — write-grant provenance (non-safe method; `Sec-Fetch-Site: same-origin` / `Origin` = app origin) | **Removable for writes.** No write grant is issued from an app request. **Replace** with the approval-endpoint provenance rule in PC-02. Read-grant provenance and `frame-ancestors 'self'` on app responses **remain**. |
| 2 — request/response filtering, cookie rules, `Service-Worker` rejection | **Still required.** |
| 3 — session / test login | **Still required.** It is now also the only approval authenticator in Phase 3, which makes PC-02 Critical. |
| 4 — "After approval, the app obtains the grant with a same-origin POST naming the pending id (R3B-04)" and the `ISSUED` state | **Removable.** Replaced by `APPROVED → EXECUTING → …`. |
| 4 — page hardening (`frame-ancestors 'none'`, COOP, CSP), "every `ledger.transfer` requires confirmation", compare-and-set state machine, approval bound to pid + session subject | **Still required** (PC-05). The ADR currently supersedes them by accident. |
| 5 — signed `cfm` marker | **Still required.** |
| 6 — grant kinds, operation-class check, read-only transactions, uniform denials | **Still required.** Write-grant TTL ≤ 30 s can stay or be shortened, since the broker receives the grant directly. |
| 7 — `exact` binding of amount/destination from the HTTP body; canonical path forwarding as a binding source | **Removable for writes.** The binding source becomes the stored proposal. |
| 7 — strict JSON, integer minor units | **Still required**, moved to `effect.propose` validation. |
| 8 — exclusions | Unchanged. |
| ADR-0003 body: route-map `confirm` predicates and write binding sources | **Removable for writes.** Replaced by per-operation declarations (needs the SI-06/SI-20 amendment). |

## Summary of blocking items

PC-01, PC-02, PC-03, PC-04, PC-05, PC-06, PC-12. All are specification changes. None requires
abandoning the design.
