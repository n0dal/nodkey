## Findings — ADR-0003

### R3-01 — Request forgery against mapped routes (High)

- **Affected:** ADR-0003 §2 (`SameSite=Lax`), §5 (route map: "method + canonical path"); THREAT_MODEL
  row A ("no session ⇒ no grant").
- **Scenarios:**
  1. *Cross-site, attacker A, no compromise.* If any mapped route uses `GET` (nothing in the ADR forbids
     it), a link or top-level navigation from any site sends `__Host-nodkey_session` (Lax cookies are
     sent on cross-site top-level GET navigations [F: RFC 6265bis §5.2/§5.8.3 "Lax"]); the gateway mints a
     grant for the victim; an honest app executes it.
  2. *Same-site, compromised sibling.* `SameSite` is about **site** (registrable domain), not origin.
     If a second Nodkey workload or any other app runs on `other.<domain>` and is compromised (C on
     workload W2), its pages can `POST` to `app.<domain>` mapped routes with the victim's cookie
     attached. The gateway mints grants with `wid = W1`; an honest W1 executes them. That is
     cross-workload authority that THREAT_MODEL §6 R-3 ("no other user's authority") and the
     multi-workload story do not mention.
  3. *App origin → auth origin.* `auth.<domain>` is same-site with the app origin, so `SameSite=Strict`
     on auth-origin cookies does **not** stop app-origin script from sending credentialed `POST`s to
     auth-origin endpoints (logout, add-passkey-begin, profile/recovery changes, "approve" in a future
     step-up flow). CORS stops reading responses, not sending simple requests.
- **Fix:** (a) Mapped (grant-producing) routes must use a non-safe method; `GET` routes are never
  mapped. (b) Gateway rejects any mapped request unless `Sec-Fetch-Site: same-origin`, or — when that
  header is absent — `Origin` equals the app origin exactly; neither present ⇒ deny. (c) Every
  state-changing auth-origin endpoint applies the same check against the auth origin, plus a
  per-ceremony CSRF token. (d) State in the ADR that separate *origin* ≠ separate *site*. (e) Add
  `verify` probes for each.
- **Blocks Phase 3 implementation:** Yes (cheap; must be in the first gateway).

### R3-02 — Auth-origin flow is underspecified (High)

- **Affected:** ADR-0003 §2 ("gateway-reserved, one-time-code callback path"); THREAT_MODEL §6 R-3
  ("Script cannot renew a session: re-authentication needs the user on the auth origin"); SI-18.
- **Scenarios:**
  1. *Login CSRF / session swap via callback.* Attacker B logs in as itself on the auth origin, stops
     before following the redirect, and keeps its one-time code. It then makes the victim's browser
     navigate to `https://app.<domain>/<callback>?code=<B's code>` (a link from any site, or one line of
     app script under C). The gateway sets B's session in the victim's browser. Nothing in the ADR
     binds the code to the browser that started the login. (Classic OAuth `state`/PKCE problem.)
  2. *Silent re-issue renews sessions from script.* The ADR does not say whether the auth origin keeps
     its own session. If it does (the usual IdP behaviour), app-origin script can do
     `location = "https://auth.<domain>/login?return_to=/x"` (or `window.open`, or a credentialed
     `fetch` that follows the redirect chain back to the callback, whose `Set-Cookie` the browser
     stores) and receive a **new** app session with no user gesture. That falsifies R-3's "cannot renew"
     and makes *L* meaningless. `frame-ancestors 'none'` does not stop top-level navigation or popups.
  3. *Fixation.* Not stated that the gateway always mints a fresh session id at callback and ignores
     any pre-existing `__Host-nodkey_session` (relevant with R3-07).
  4. *`return_to` / open redirect.* Not specified; an unvalidated return target on the auth origin
     leaks the code to an attacker host.
  5. *Host routing.* If app and auth hosts share a certificate (wildcard or SAN) and address, HTTP/2
     connection coalescing can deliver auth-host requests on the app's connection [F: RFC 9113 §9.1.1];
     the gateway must route on `:authority`/`Host`, never on SNI, and answer `421` on mismatch.
- **Fix:** Specify the flow as a mini-OIDC code flow: login initiation by the gateway on the app host
  sets a short-lived `__Host-nodkey_login` state cookie (random) and passes its hash to the auth
  origin; the code is bound to that state and to a PKCE-style verifier, single-use, ≤ 60 s; callback
  rejects codes whose state cookie is absent or different; `return_to` is a same-origin path from an
  allowlist; fresh session id at callback; **every** session establishment requires a WebAuthn
  assertion with user verification (no silent re-issue), or else R-3 must state the auth-origin session
  lifetime as the true bound; state *L* (absolute and idle) numerically.
- **Blocks Phase 3 implementation:** Yes.

### R3-03 — Exact binding does not bind the *user's* request against attacker C (High)

- **Affected:** ADR-0003 evaluation criteria ("the effect is bound to the user's actual request"),
  Residual §"In-flight grant", Consequences ("residual equals the user's own request for exact
  routes"); THREAT_MODEL R-2; ARCHITECTURE §3 last paragraph.
- **Scenario:** The user types `$25` into a refund form. The form, the submit handler, and the
  `fetch` call are app-origin code. Under C, the script submits `{"amount_cents": 250000}` to
  `/orders/9822/refund` (or to a transfer route with the attacker's destination). The gateway parses
  this faithfully, binds `== 250000`, and the broker executes exactly that. The grant is "exactly the
  request", but the request is not the user's intent. The route map cannot tell the two apart because
  both arrive with the same cookie, origin and `Sec-Fetch-*` values.
- **Assessment:** Against C *while a user is active*, exact binding adds nothing beyond R-3; R-2 is a
  subset of R-3. Exact binding still has real value: (1) a grant cannot be widened, reused, or redirected
  after issue (SI-06/07); (2) honest-app correctness; (3) it is the necessary substrate for the only
  control that does bind intent — a confirmation rendered on the **auth origin** that shows the bound
  values (`op`, `res`, `con`) and requires a user-verifying WebAuthn assertion before signing
  (WYSIWYS / transaction confirmation). THREAT_MODEL already lists this as "future gateway-origin
  approval for high-value ops".
- **Fix:** Rewrite the criterion to "the effect is bound to the request the browser sent"; state
  explicitly that under C this equals R-3 and that intent is bound only on routes marked `confirm`
  (auth-origin confirmation). Make `confirm` mandatory for destination-like parameters (new payee,
  transfer destination) before any claim beyond R-3 is published. Remove "residual equals the user's own
  request" from Consequences.
- **Blocks Phase 3 implementation:** No. Blocks acceptance (SI-17 honesty).

### R3-04 — Reads and page composition have no design (High)

- **Affected:** ADR-0003 §5 ("at most one operation per request"), §8 ("Unmapped routes get no grant");
  ADR-0009 §3 (no grantless op in multi-tenant workloads); SI-19.
- **Evidence:** The Demo 1 broker already has `ledger.get_balance` (`broker/src/protocol.rs`,
  `broker/src/config.rs`). Reads of protected rows are protected effects under the SI Terms table
  ("access or mutation").
- **Scenario/problem:** A typical page renders several reads (balance, recent transfers, order list).
  Either (a) each read needs a `user_grant` — but a request maps to at most one operation, so the page
  cannot be built, and every page view costs a signature; or (b) reads are `workload` operations —
  forbidden in multi-tenant workloads, and in single-tenant ones they let C read **every** user's data
  with no subject (R3-14); or (c) reads are quietly exempted — an undeclared grantless path, which is
  exactly what SI-19 forbids.
- **Fix:** Decide explicitly. One workable option: a `read` grant kind per mapped request carrying
  `(ten, sub)` and a declared *set* of read operations, multi-use within its TTL, never accepted by
  write operations; reads still filter by grant-sourced `ten`/`sub` in-query. Then state that AR-13's
  one-op rule applies to effects (writes), and add the read residual (C reads whatever the active user
  can read, R-5) to the table.
- **Blocks Phase 3 implementation:** Yes (Demo 2 needs balances).

### R3-05 — Exact binding implementability; non-bindable classes not stated (Medium)

- **Affected:** ADR-0003 §5; ADR-0004 `con`; ARCHITECTURE §3 step 3.
- **Problems:**
  1. *Encoding.* §5 parses JSON only. Legacy PHP forms post `application/x-www-form-urlencoded` or
     `multipart/form-data`, where PHP's own parser applies `a[]`/`a[b]` nesting, last-wins duplicates,
     and `.`/space → `_` name mangling. Either JSON-only is a stated Native-mode requirement, or the
     gateway needs a strict urlencoded grammar (duplicates rejected, no brackets) — and the ADR should
     say which.
  2. *Typing.* The user types `25.00` (or `25,00`); the operation takes `amount_cents: 2500`. The route
     map needs declared, deterministic conversions; none are specified.
  3. *Values not in the request.* ARCHITECTURE §3 binds `currency: ==USD`, which is not in the body.
     §5 says exact values "come from the request". A third source — route-map constants — exists
     implicitly; values that depend on DB state (the order's currency) have no source at the gateway,
     which has no DB access.
  4. *Classes that cannot be exact:* server-computed amounts (cart totals, tax, shipping, FX, pro-rata
     refunds) → `bounded` at best; app-resolved destinations ("pay alice@…" → account id) — destination-
     like, so neither `free` nor meaningfully `bounded`: **such operations cannot be served at all**
     unless the broker does the resolution; app-generated identifiers (new order id, idempotency key);
     multi-step wizards whose final POST carries no values; free text and file content (bind by hash or
     declare `free`); batches/lists.
  5. The ADR's three classes are right, but it does not tell adopters which common patterns fall where,
     and the fail-closed outcome for (4)-destinations is not stated.
- **Fix:** Add a "binding source" column per parameter (`request:<json-pointer>` | `route:<constant>` |
  `bounded:<ceiling>` | `free:<justification>`), the conversion grammar, the encoding decision, and a
  short table of the patterns above with their class and residual. State that app-side resolution of a
  destination is unsupported by design; move resolution into a broker operation.
- **Blocks Phase 3 implementation:** Yes for (1)–(3) (the gateway parser cannot be written without
  them); (4)–(5) are documentation.

### R3-06 — Content-type-keyed cache controls are bypassable (Medium)

- **Affected:** ADR-0003 §4 ("sets `Cache-Control: no-cache` on HTML and JavaScript responses");
  THREAT_MODEL R-3 "Who".
- **Scenario:** C serves its persistent payload as `/static/app.js` with `Content-Type:
  application/octet-stream` and `Cache-Control: max-age=31536000, immutable`. Without
  `X-Content-Type-Options: nosniff`, browsers execute classic scripts with most non-JS MIME types
  [F: Fetch "should response to request be blocked due to its MIME type?" blocks only `audio/*`,
  `image/*`, `video/*`, `text/csv`]. The gateway does not classify it as JS, so the year-long cache
  survives remediation. HTML-capable types (`image/svg+xml`, `application/xhtml+xml`, XML) evade the
  "HTML" rule the same way. Duplicate `Content-Type` headers create further ambiguity.
- **Dependency:** The service-worker block (fact-check (a)) assumes the browser's SW script fetch
  reaches the gateway. With `register(url, {updateViaCache: 'all'})` the fetch hook does not force
  `no-cache`, so a JS-typed response cached earlier could satisfy it from the HTTP cache **[H, spike]**.
  The block is therefore only as strong as the cache rule.
- **Fix:** Apply the cache override to **every** app response (replace `Cache-Control`, drop `Expires`,
  `Age`, `Last-Modified`-based heuristics), with an optional allowlist of content-hashed static paths
  from a deploy manifest; always add `X-Content-Type-Options: nosniff`; reject `Service-Worker` request
  headers by **presence** (any value, any case); collapse or reject duplicate `Content-Type`.
- **Blocks Phase 3 implementation:** No; blocks any SI-18/R-3 claim.

### R3-07 — App script can set gateway-owned cookie names (Medium)

- **Affected:** SI-18 ("workload responses cannot set them"); ADR-0003 §4.
- **Scenario:** When the victim has no session (logged out, expired), app-origin script runs
  `document.cookie = "__Host-nodkey_session=<B's session id>; Secure; Path=/"`. This satisfies every
  `__Host-` requirement (secure origin, `Secure`, `Path=/`, no `Domain`) [F: RFC 6265bis storage model
  §5.7 step 21]. The HttpOnly protection only stops script from *overwriting an existing* HttpOnly
  cookie (§5.7 step 23.2); a cookie-jar overflow can evict the existing one first (UA "remove excess
  cookies" is permitted at any time, §5.7) **[H: per-browser limits]**. `__host-nodkey_session` is a
  distinct cookie with the same prefix rules (prefix match is case-insensitive in the storage model),
  so the gateway may receive two candidate session cookies. Impact under C is mainly session swap
  (victim acts inside B's account, R3-02.1 by another route) — low authority gain, but SI-18's text
  claims more than the mechanism gives.
- **Fix:** Gateway rejects any request carrying more than one cookie whose name matches
  `__host-nodkey` case-insensitively; response filter drops `Set-Cookie` by case-insensitive prefix
  and, preferably, forwards app `Set-Cookie` only for allowlisted app cookie names (symmetric with the
  request allowlist); SI-18 reworded to "the workload cannot cause a gateway-owned cookie to be
  *accepted* as a session other than one the gateway issued to this browser" or the residual stated.
- **Blocks Phase 3 implementation:** No.

### R3-08 — R-8: the gateway's app-facing parser is unspecified (Medium)

- **Affected:** ADR-0003 Consequences (Security); THREAT_MODEL R-8, TB-2.
- **Gaps:** No statement on: connection reuse between gateway and app (with keepalive or pipelining an
  app that emits two responses for one request desynchronises association — the same class AR-07 raised
  for nginx); `101 Switching Protocols`/`Upgrade` (turns the connection into an opaque tunnel past every
  filter); `1xx`/`103 Early Hints` forwarding; trailers; conflicting `Content-Length`/
  `Transfer-Encoding`; obs-fold; response size and time caps; response headers handled by denylist
  (§4 lists three drops) rather than allowlist. And the session table lives in the same process that
  parses attacker bytes, so any logic bug there yields every live session.
- **Fix:** Specify: HTTP/1.1 over UDS, one request per connection (or strict ordered association with
  a per-request id the gateway checks), no upgrades, no 1xx forwarding, no trailers, strict framing,
  caps, a response-header allowlist. Evaluate splitting the gateway into an edge process (TLS, sessions,
  auth origin) and an app-proxy process that holds no session table and receives only the already
  allowlisted request plus grant; that turns R-8 from "all live sessions" into "requests in flight".
  If rejected for cost, say so in the ADR.
- **Blocks Phase 3 implementation:** No, but must be in the Phase 3 gateway spec.

### R3-09 — Enrollment and recovery are the unaddressed credential (Medium)

- **Affected:** ADR-0003 Residual ("No credential capture under passkeys"); THREAT_MODEL R-4.
- **Scenario:** A passkey cannot be phished on the app origin (fact-check (b)), so C shows "your passkey
  failed — enter the recovery code we emailed you" on the app origin. Whatever bootstraps a passkey
  (first enrollment, new device, lost device) is the real credential, and the ADR does not name it.
- **Fix:** State the enrollment and recovery mechanisms, require them to complete on the auth origin
  only, and add "recovery-code phishing on the app origin" to R-4 with the same honesty as the password
  profile.
- **Blocks Phase 3 implementation:** No; blocks the R-4 claim.

### R3-10 — Simpler alternative not evaluated (Medium)

- **Affected:** ADR-0003 Alternatives.
- **Point:** The auth origin, passkey ceremonies, recovery, and session management are commodity
  functions of open-source IdPs (OIDC providers with WebAuthn) and identity-aware proxies (e.g. the
  oauth2-proxy / Pomerium pattern of a proxy that terminates sessions and forwards an allowlisted
  request with a signed per-request assertion). The Nodkey-specific part is the route map, exact
  binding, and the grant signer. Writing WebAuthn and session code in a new TCB component enlarges it
  where existing tools already exist (owner directive: "prefer existing tech"). The ADR mentions this
  only under Reversal.
- **Fix:** Add the "existing OIDC IdP on `auth.<domain>` + Nodkey gateway as OIDC RP" alternative with
  a reasoned verdict (it also resolves most of R3-02 by reusing a reviewed code flow). Keep the custom
  path only if it is shown to be smaller or required.
- **Blocks Phase 3 implementation:** No.

### R3-11 — Smaller gaps (Low)

1. The forwarded request should carry the **canonical** path the gateway mapped and the exact query
   string; state which request parts (path, query, body) may feed exact values. AR-07 item 3 is not
   restated in rev. 2.
2. OQ-08 "addressed by single-parser topology" is true only in effect: the app re-parses the body with
   PHP; divergence makes an honest app submit different values, which the broker denies for `exact`
   parameters (fail-closed) and does not detect for `bounded`/`free`. Say that instead.
3. Auth-origin pages should send `Cross-Origin-Opener-Policy: same-origin` (an app-opened login popup
   can otherwise be navigated by its opener to a look-alike) and a strict CSP with no app-origin
   sources.
4. R-3 "while a tab is open": popunders opened on a user click and `fetch(…, {keepalive: true})` at
   unload extend this slightly; state it.
5. The `Clear-Site-Data` runbook omits app cookies that a patched app reads; note the gap or include
   `"cookies"` with a forced re-login.

## Findings — ADR-0009

### R3-12 — The scheduler adds components but no authority check (High)

- **Affected:** ADR-0009 Decision 1; ARCHITECTURE §1 (Scheduler, TCB); THREAT_MODEL R-16.
- **Analysis:** The scheduler reads broker state with a read-only role, finds a precondition, and signs
  a grant whose `ten`, `sub`, `res`, and exact parameters are **copied from the broker's own record**.
  The broker then verifies the signature and re-checks the same precondition in-transaction (ADR-0007
  §2). The signature attests facts the broker already holds; this is the circularity AR-17 identified
  for `sub`/`ten`, moved to a new component. The worker still chooses which job to claim and when, so
  the scheduler does not restrict selection or timing either. What it adds: a TCB container, a signing
  key, a second `iss`, a queue, a claim operation, and a TTL problem (R3-13).
- **Simpler equivalent:** A `derived` authority class. The workload submits only the workflow id; the
  broker locks the workflow row, takes `ten`, `sub`, `res`, and every parameter from it, checks that the
  row's precondition was created by a committed `user_grant` effect (store the consuming `jti` on the
  row), and applies the declared transition. Same guarantees, multi-tenant safe (the tenant comes from
  the row, never the app), no new component. If the scheduler is meant to add something — a not-before
  time, rate limiting, operator holds — the broker can enforce those as guards; the ADR must name it.
- **Fix:** Replace the scheduler with broker-derived authority, or state precisely which property the
  scheduler provides that the guard cannot.
- **Blocks Phase 3 implementation:** Yes for the design decision (AR-06 was a Phase 3 design blocker);
  the implementation is Phase 5.

### R3-13 — Internal contradictions in Decision 1–3 (High)

1. **`job.claim` is an undeclared grantless operation.** The worker calls it without a grant, in
   multi-tenant workloads, and it changes state (claims the job) and returns a grant. Decision 3 says a
   grantless operation in a multi-tenant workload is a startup error. Its authority class is not
   declared, and SI-19's falsifier ("an effect without a verified grant for any other operation") is
   met by design.
2. **Read-only scheduler writes a queue.** "Read-only DB role" and "places `{job, grant}` in a
   broker-owned queue" conflict; either it has a write role (state it, with table-level grants) or it
   calls the broker (another socket and operation to declare).
3. **TTL.** ADR-0004 caps `exp − nbf` at 30 s unless a route gives a written reason. Background queues
   routinely exceed 30 s; grants expire in the queue. Either scheduler grants carry long TTLs (larger
   R-16, needs the written reason) or the scheduler signs on claim (it is on the request path).
4. **"Steps that need app computation"** cannot exist if every parameter is copied from the broker
   record. Any app-computed parameter is not covered by the copying rule and is unclassified.
5. **Budgets** for scheduler-granted effects (charged or not, to which scope) are unstated.
6. **Broker-internal steps "on the same trigger"**: the trigger is undefined (time? a workload call?).
   If time-based, the broker gains a scheduler; if call-based, name the operation that carries it.
- **Fix:** Resolve each explicitly; most disappear with R3-12's derived class.
- **Blocks Phase 3 implementation:** Yes (design), with R3-12.

### R3-14 — The `workload` class has no subject and spans all users of the tenant (High)

- **Affected:** ADR-0009 Decision 3 and Advantages ("every effect has a trusted tenant and subject");
  SI-19; THREAT_MODEL R-7.
- **Scenario:** A single-tenant workload with 10,000 users declares `orders.expire_stale` (or
  `ledger.adjust`) as `workload`. There is no grant, hence no `sub` and no exact value for any
  parameter; the app chooses the resource. C applies the operation to any user's order, up to the
  ceiling per call and the budget. "Destination-like parameters are forbidden" does not cover resource
  identifiers. For non-monetary effects (delete, state change, cancel) a "per-call ceiling" has no
  meaning. Separately, "single-tenant" is an operator assertion: nothing stops user grants for other
  tenants reaching that `wid`.
- **Also:** The Demo 1 operations (`ledger.transfer` with `from`/`to`, `ledger.get_balance` with
  `account`) are effectively `workload` operations with a destination-like parameter. Under ADR-0009
  they are not allowed. Phase 3 must migrate them (state it in STATUS/ROADMAP).
- **Fix:** Remove "every effect has a trusted subject" or define `sub = wid` for workload ops; require a
  declared resource scope (e.g. only rows created by the workload, or only non-user-owned rows); require
  a count budget for non-monetary ops; have the broker deny any grant for a single-tenant `wid` whose
  `ten` differs from the registered tenant, and the gateway refuse to route other tenants' users there;
  publish "affects any user of the tenant" in R-7.
- **Blocks Phase 3 implementation:** No (no workload ops planned for Demo 2 once R3-04 is decided);
  SI-19 text must change before acceptance.

## Was the design simpler than it could be?

No, in two places. (1) ADR-0009's scheduler can be deleted in favour of broker-derived authority with
identical guarantees (R3-12). (2) ADR-0003's auth origin and session handling duplicate open-source IdP
and identity-aware-proxy functions; only the route map, binding, and signer are new (R3-10). The
separate authority container is justified (it keeps the key out of the process that parses app output,
so a gateway compromise ends when the gateway is fixed), but the ADR should say that it gives no
protection for live sessions while the gateway is compromised: the authority signs whatever the
gateway asks.

### R3B-01 — Threshold confirmation is bypassed by splitting (High)

- **Affected:** §6 "Which routes confirm" (`confirm: {when: amount_cents > threshold}`); R-16; SI-20.
- **Scenario (C, user has a tab open):** app script sends `POST /transfer` *n* times with
  `amount_cents = threshold` (or `threshold − 1`) to the attacker's account. Each request passes §3
  (same-origin), each gets a write grant with no confirmation, the broker executes each. Total loss is
  bounded only by the balance and by whatever generic `(ten, sub)` budget ADR-0006 configures, not by the
  threshold. R-16 describes the destination as "not intent-bound" for small transfers but does not say
  that the threshold does not bound the *total*. A demo claim like "large transfers need the user's
  passkey" is therefore misleading under C.
- **Fix (pick one for Phase 3):** (a) confirm **every** `ledger.transfer` (simplest; removes the
  predicate machinery from the demo); or (b) keep the threshold and add a broker-enforced
  **unconfirmed-value budget** per `(ten, sub, window)` (ADR-0006 counter row), charged only by grants
  without a confirmation claim (R3B-02); publish "loss under C without the user's passkey ≤ B per
  window". The recommended "confirm new destinations" rule also closes the theft path (C needs a new
  destination) and could replace (b) — it needs broker-held "confirmed destinations" state.
- **Blocks Phase 3:** Yes, for the demo's security claim.

### R3B-02 — The broker cannot see whether a grant was confirmed (Medium)

- **Affected:** §6, §7, §8; ADR-0004 (pending amendment).
- **Scenario:** `confirm` is a route-map attribute evaluated only by the edge. (1) Two routes map to
  `ledger.transfer`, one without `confirm` (route-map error or later edit): the weaker route issues
  unconfirmed grants for large amounts and the broker accepts them. (2) An edge bug in predicate
  evaluation (e.g. `>` vs `>=`, unit conversion) is invisible downstream. SI-20 is then falsified with no
  second check. This does not defend against edge compromise (the authority signs anything), only against
  misconfiguration and edge bugs — but those are the likelier failures.
- **Fix:** attach the `confirm` policy to the **operation** (one place), not the route. Add to the
  ADR-0004 amendment a signed claim `cfm = SHA-256(challenge)` (or the pid) present only on grants from
  §6 step 5. The broker evaluates the same predicate over the grant's exact values and denies a
  confirm-required effect without `cfm`; it charges unconfirmed grants to the R3B-01 budget. Startup
  check: every route mapping a `confirm` op inherits it.
- **Blocks Phase 3:** Yes, as part of the already-blocking ADR-0004 amendment.

### R3B-03 — Opaque identifiers make the summary unverifiable (Medium)

- **Affected:** §6 step 3 and "Display names"; §5 table ("broker generates ids").
- **Scenario:** the question asked whether attacker-chosen display names can confuse the summary.
  Rev. 3 avoids that by showing **no** names — but then the destination is `acct_9f2c…`, an id the broker
  generated and the user has never seen. The user can verify the amount but not the payee, so for the
  destination SI-20 is satisfied in letter ("approved a summary of the exact values") and not in
  substance. If ids are ever user-chosen, the `[A-Za-z0-9_-]` grammar still allows look-alikes (`l`/`1`,
  `O`/`0`). Free-text fields (memo) need bidi/control-character neutralisation, not just HTML escaping
  (U+202E can reorder the visible summary) **[H on rendering details]**.
- **Fix:** for v1/demo, show (a) a broker-sourced **"first transfer to this account"** flag, and (b) a
  name the **user** assigned to the destination on the auth origin (a pet name), never a name the
  destination's owner chose; render ids in a monospace, confusable-safe font. Strip or visibly escape
  Unicode bidi/format characters (Cc, Cf) in free text and render it in a box labelled as app-supplied.
  Until then, document that the confirmation binds the *amount* and *source account*, and that
  destination recognition is by opaque id (extend R-16).
- **Blocks Phase 3:** No (the demo can ship with the narrower claim stated).

### R3B-04 — Continue step contradicts SI-21 (Medium)

- **Affected:** §6 step 5; SI-21.
- **Scenario:** the browser reaches `/.nodkey/continue/<pid>` by a redirect from the auth origin: a
  `GET` with `Sec-Fetch-Site: same-site` (or `cross-site` under the recommended separate registrable
  domain). The edge then issues a **write** grant. SI-21 is falsified by "a write grant issued for a safe
  method, a cross-origin … request". An implementer must either violate SI-21 or break the flow. Risk is
  low (the pid is unguessable, P is single-use and already confirmed, and the session must match
  `P.sub`), but the invariant as written is false.
- **Fix:** amend SI-21: "…or at `/.nodkey/continue/<pid>` for a pending effect whose originating request
  passed this check and which is `CONFIRMED` for the session's subject." Also require that path to be
  `GET` with `Sec-Fetch-Mode: navigate`, `Sec-Fetch-Dest: document`, and send `Referrer-Policy:
  no-referrer` on auth pages (the pid is in URLs).
- **Blocks Phase 3:** Yes (text only).

### R3B-05 — `navigate` is not "top-level" (Medium)

- **Affected:** §3 read-grant rule; SI-21 ("top-level navigations"); R-18.
- **Scenario:** Fetch Metadata sends `Sec-Fetch-Mode: navigate` for nested (iframe) navigations too;
  `Sec-Fetch-Dest` distinguishes `document` from `iframe` [F: W3C Fetch Metadata Request Headers,
  `Sec-Fetch-Mode`/`Sec-Fetch-Dest` definitions — not re-fetched in this pass]. A cross-site page frames
  `GET /balance`; the edge issues a read grant; the victim's balance renders inside the attacker's page.
  Contents are not readable cross-origin, but the frame enables UI redress over app controls and XS-Leak
  probing (frame counting, timing). Rev. 3 adds `frame-ancestors` only to the auth origin.
- **Fix:** for non-same-origin read requests require `Sec-Fetch-Mode: navigate` **and**
  `Sec-Fetch-Dest: document`; the edge sets `Content-Security-Policy: frame-ancestors 'self'` (or
  `'none'`) on every app response, overriding the app. State that absent Fetch Metadata headers mean deny
  for reads (fail-closed, as the current wording implies).
- **Blocks Phase 3:** Yes (two header checks).

### R3B-06 — Read grants: no cross-user read found; "not a write path" is unenforced (Medium)

- **Cross-user reads:** none found in the design. `sub`/`ten` come from the grant and ownership is
  evaluated by the broker on trusted rows. Residuals: (1) a read op whose result joins another subject's
  row (counterparty name or balance on a transfer record) leaks across users; (2) different errors for
  "no such account" and "not yours" give an existence oracle for other users' account ids.
- **Write path:** the only barrier is "a read grant is never accepted by a write operation", which
  depends on a grant-kind field that ADR-0004 does not have yet. If the kind is missing, defaulted or
  unchecked, a multi-use read grant presented to `ledger.transfer` is a **replayable** write grant for
  30 s (the `jti` single-use check might be skipped for read-kind). A read op with a side effect (audit
  row, "last viewed", lazy initialisation) is a write reachable by read grant.
- **Fix:** ADR-0004 amendment: `kind` is a signed, required field; unknown kind ⇒ deny; the op registry
  declares `class: read|write` and the broker rejects any kind/class mismatch **before** dispatch. Read
  ops run in a database `READ ONLY` transaction, so a write from a read op fails structurally. Read ops
  return the same denial for not-found and not-owned, and may not return columns of rows owned by other
  subjects. Negative tests for each.
- **Blocks Phase 3:** Yes (with the ADR-0004 amendment; `get_balance` is the demo read).

### R3B-07 — Pending-effect state machine and challenge encoding (Low)

- **Scenarios:** (1) *Approval replay:* the challenge is deterministic in `(pid, values)`; nothing states
  that an approval for a `USED` or expired P is rejected rather than re-marking it `CONFIRMED`. (2) *Two
  continues in parallel* (two tabs, or script racing the redirect): "unused" must be an atomic
  transition or two grants are signed. (3) `‖` concatenation of `canonical(op, res, con)` must be
  injective. (4) *Racing a second P into the confirmation:* script can create P2 and steer the popup to
  `/confirm/<P2>`; this is safe only because each page renders and verifies **its own** P — the approve
  endpoint must take pid from the page's own form and recompute the challenge from stored P, never from
  request-supplied values. Background tabs cannot run a WebAuthn get without focus **[H]**, so cross-tab
  approval of a hidden P requires user action on that tab.
- **Fix:** state P's transitions `PENDING → CONFIRMED → USED` as compare-and-swap, terminal on
  reject/expiry; approval accepted only from `PENDING`, continue only from `CONFIRMED`; canonical
  encoding = deterministic CBOR (as ADR-0004) with domain tag; challenge recomputed server-side from
  stored P. Tests: double-approve, double-continue, approve-after-expiry, approve P1's assertion against
  P2.
- **Blocks Phase 3:** Yes (cheap; it is the implementation spec).

### R3B-08 — Clickjacking residue (Low)

- **Scenario:** framing is blocked (`frame-ancestors 'none'`, COOP). Remaining: "double-click"
  window-swap attacks (app opens the confirm popup under the user's cursor between two clicks) and
  popunder timing. The UV ceremony is a second, OS-level gesture, so a stray click alone does not approve;
  the remaining risk is habituation (the app shows a fake app-origin "summary" of benign values, then the
  real auth page shows malicious ones and the user completes the passkey without reading).
- **Fix:** Approve enabled only after the page has been visible and focused for ≥ 500 ms and after a
  fresh pointer-down on the button; auth page states "Check these values; the app cannot change this
  page". Publish habituation as a residual of SI-20 (WebAuthn UI does not show the values).
- **Blocks Phase 3:** No.

### R3B-09 — Edge/proxy split: removable for Phase 3 (Low, simplicity)

- **Finding:** no SI depends on the split. What it buys: a memory-safety or logic bug in the HTTP/1.1
  **response** parser (bytes from C) does not run in the process holding TLS keys and sessions. The
  strict profile (one request per connection, no upgrade/1xx/trailers, strict framing) gives the
  smuggling/desync protection, and it works in-process too. The edge still parses (a) every browser
  request — attacker bytes from A, B and C's script — and (b) the proxy's structure, whose header values
  and bodies are attacker-chosen. So the Consequences line "attacker-byte parsing runs in a process that
  holds no secrets" is over-claimed.
- **Fix:** for Phase 3, keep the HTTP profile, drop the process split, and state R-8 at its previous size
  ("all live sessions") — or keep the split and correct the Consequences sentence to "workload-response
  HTTP framing". Revisit the split after a parser-fuzzing result.
- **Blocks Phase 3:** No.

### R3B-10 — Script-triggered re-login (Low)

- **Scenario:** no silent re-issue holds (the auth origin keeps no session). But C can navigate the top
  level to the login page at any time ("session expired"); a user who completes the ceremony renews the
  session. *L* bounds C only if the user declines. Login CSRF and fixation are otherwise handled: the
  `__Host-nodkey_login` binding, fresh session id and duplicate-cookie rejection hold against A/B; under
  C, script can pre-plant its own login cookie before a callback (no existing cookie) — that is R-17, which
  the confirm-page `P.sub` check covers.
- **Fix:** add the re-login prompt to R-3's text; the login page shows "You were sent here by <app>; only
  continue if you meant to sign in."
- **Blocks Phase 3:** No.

### R3B-11 — Local test login vs SI-18/SI-20 (Low)

- **Scenario:** the demo's "local test login" does not meet SI-18 (session established without a WebAuthn
  ceremony on the auth origin). SI-20 needs a WebAuthn credential bound to `P.sub`, so the demo needs
  passkey enrollment anyway. If the test login is reachable in a non-demo build, it is an insecure
  fallback (owner directive: dev bypasses explicit, isolated, impossible to enable accidentally).
- **Fix:** either log in with the same passkey used for confirmation (cost is small once WebAuthn is in),
  or compile the test login behind a feature flag absent from release builds, label SI-18 *NOT TESTED* in
  the demo, and use a virtual authenticator for automated confirm tests.
- **Blocks Phase 3:** Yes (labeling and build isolation).

### Answers to the questions asked

- **Does confirm stop a compromised app origin from getting a confirm-required grant for values the user
  did not approve?** Yes, for a single effect, provided R3B-07 is implemented: the page is not frameable
  or scriptable, values come only from P, the challenge commits to them, and the credential must be
  `P.sub`'s. Racing a second P, cross-tab, and replay are safe with the stated state machine. Remaining:
  habituation (R3B-08), opaque destinations (R3B-03), and — the main gap — splitting below the threshold
  (R3B-01).
- **Read grants:** no cross-user read in the design; a write path exists only if the grant kind is not
  enforced (R3B-06).
- **Proxy split:** removable for Phase 3 without losing an SI (R3B-09).
- **Unnecessary for the demo:** the proxy split; IdP delegation; recovery codes and invitation enrollment
  (one pre-enrolled user per test); urlencoded parsing (JSON only); `state:` binding source; deploy-manifest
  static cache exception; the `confirm: {when}` predicate if R3B-01(a) is chosen.

### Minimal subset of rev. 3 the Phase 3 demo must implement for honest claims

1. §3 write provenance (non-safe method; `Sec-Fetch-Site: same-origin` else exact `Origin`; else deny)
   and read provenance with R3B-05 (`navigate` + `document`, edge-set `frame-ancestors`).
2. §4 request/response filtering already required by SI-18: gateway cookies/headers never forwarded,
   duplicate gateway cookie rejection, `Set-Cookie` allowlist, `Service-Worker` rejection, `no-store`,
   `nosniff`.
3. Session: `__Host-nodkey_session` HttpOnly/Secure/Lax, fresh id on login, absolute *L*, logout
   revocation. Login: passkey on the auth origin with the state/verifier callback binding and
   `return_to` allowlist — or the test login per R3B-11, with SI-18 labelled *NOT TESTED*.
4. §6 confirmation, in full, with R3B-07 (CAS state machine, server-side challenge recomputation, RP ID =
   auth host, `C.origin` check, credential ∈ `P.sub`), R3B-04 (SI-21 continue exception), and auth-page
   `frame-ancestors 'none'`/COOP/CSP.
5. R3B-01: confirm every transfer, **or** threshold + broker unconfirmed-value budget; plus R3B-02's
   `cfm` claim checked by the broker.
6. §7 grants: single-use 30 s write grant; read grant for `ledger.get_balance` with R3B-06 (signed
   `kind`, class match before dispatch, `READ ONLY` transaction, uniform denial). Requires the ADR-0004
   amendment.
7. §5 strict JSON with `minor_units` and `id` conversions, `exact` binding, canonical path forwarding.

### Verdict

**Accept with listed changes:** R3B-01, R3B-02, R3B-04, R3B-05, R3B-06, R3B-07 and R3B-11 before Phase 3
implementation; R3B-03 and R3B-09 as text corrections before acceptance; R3B-08 and R3B-10 as published
residuals. No High finding remains once R3B-01 is resolved by either option.
